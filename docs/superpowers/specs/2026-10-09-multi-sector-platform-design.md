# Multi-sector platform: super admin, organisations by category, public site from the laptop — Design Spec

**Date:** 2026-10-09
**Status:** awaiting owner review
**Builds on:** `2026-10-06-qcertchain-design.md` and everything in `docs/`. Where this spec and an earlier decision
conflict, this spec wins only for the items listed in §9, each decided with the owner on 2026-10-09.

---

## 1. Intended outcome

QCertChain stops being a two-bank demo and becomes a platform any sector can join.

- A **super admin** signs in with an email and a password and creates organisations, each in a **category**.
- Every organisation, old or new, gets the **same workflow**: its sector's live candidates, campaigns, interdiction,
  evidence, ledger.
- The **login page** offers both doors: pick an organisation (read-only, one click) or sign in as super admin.
- Anyone opening the public site on their own laptop sees it working, served from the owner's laptop through a free
  Cloudflare quick tunnel (`trycloudflare.com`) whose changing URL the site discovers by itself.
- A viewer **understands what they are looking at** without the presenter: a **Technical approach** page, a guided
  **How it works** tour through the real pages (Next step, Next step), and a **?** on every page explaining it.

**Success looks like:** on the public site, the super admin creates "ShopSafe SOC" in E-commerce; it appears on the
login page with its read-only key; signing in as it shows a seeded Flipkart-themed campaign, its graph and plan, a
signed and anchored evidence bundle, and the Ledger lookup returns its campaign; Bank One's data stays a 404 for it.

## 2. Approach

**Extend what exists** (approach A, chosen 2026-10-09). The API-key model, row-level security, the ledger and the
pipeline stay; everything hard-wired to "org1 and org2" is generalised to "every organisation in the database".
Rejected: full per-person user accounts (rewrites auth, console sign-in and the demo-key model; too large) and a thin
UI over `scripts/create_api_key` (new organisations could not use the ledger and would get no sector feed).

No new Python or npm dependency: PyNaCl (argon2id, SecretBox), `eth_account` and `web3` are already installed.
`cloudflared` is run through `npx` as a tool, not a project dependency (§10). The console reads one Supabase row with
plain `fetch` (no Supabase client library). The guided tour is built in the console (no tour library).

## 3. Data (`services/api/schema.sql`, idempotent, applied after a backup per `MIGRATION_RUNBOOK.md`)

**`organisations`** gains:

| Column | Type | Notes |
|---|---|---|
| `category` | `text not null default 'other'` | check in `banking, fintech, ecommerce, government, telecom, brokerage, insurance, consumer, other`; existing rows set to `banking` |
| `active` | `boolean not null default true` | a deactivated organisation's keys stop working |
| `chain_address` | `text` | its account on the demo chain; org1/org2 get Hardhat #1/#2 |
| `chain_key_sealed` | `bytea` | its chain private key, sealed (below); null for org1/org2 (theirs stay in `.env`) |
| `demo_brand` | `text` | the brand its seeded campaign imitates |
| `created_at` | `timestamptz default now()` | "oldest active organisation in a sector" (§5) |

**`api_keys`** gains `token_sealed bytea` (the token, sealed) and `expires_at timestamptz` (sessions only). The kind
check becomes `org, demo, admin, superadmin`; `superadmin` has no organisation, like `admin`.

**Sealing.** `token_sealed` and `chain_key_sealed` are encrypted with `nacl.secret.SecretBox` under `KEY_SEAL_SECRET`
(32 random bytes, hex, in `.env`, generated by `python -m scripts.genkey --seal`). The hash stays the lookup path;
the sealed copy exists only so the panel and the login page can show a key again. **This changes the rule "a key is
shown once" (§9).** Without `KEY_SEAL_SECRET` the API still runs; keys are then shown only at creation.

**Existing keys.** Today's keys exist only as hashes. `python -m scripts.superadmin backfill` seals the keys already
in `.env` (`QCC_KEY_ORG1`, `QCC_KEY_ORG2`, `QCC_KEY_DEMO`) after checking each against its stored hash, and creates
the missing read-only key for org2 (sealed). The admin key is never sealed or shown.

**`super_admins`** (`id`, `email unique`, `password_hash`, `created_at`). The hash is argon2id
(`nacl.pwhash.argon2id.str`). `python -m scripts.superadmin set` upserts the account from `SUPERADMIN_EMAIL` and
`SUPERADMIN_PASSWORD` in `.env` (never from argv, so the password stays out of shell history); `scripts.demo up` runs
it. Row-level security: no `qcc_app` policy, so no organisation-scoped connection can ever read it.

## 4. API (`docs/API_CONTRACT.md` updated in the same change)

| Route | Key | Does |
|---|---|---|
| `POST /auth/superadmin/login` `{email, password}` | none | argon2id check; returns `{token, expires_at}`: a `qcc_superadmin_…` key, 12 h, hash-only (never sealed) |
| `POST /auth/logout` | any | revokes the calling key if it is a superadmin session; for any other key it does nothing (204) |
| `GET /orgs/public` | none | `[{slug, name, category, demo_key}]` for active organisations; **only demo (read-only) keys**, ever |
| `GET /superadmin/orgs` | superadmin | every organisation, category, active, chain status, key prefixes, created |
| `POST /superadmin/orgs` `{name, category, demo_brand?}` | superadmin | creates the organisation, an org key and a demo key (sealed), its chain account (funded + registered), its seeded campaign (§6); returns both keys |
| `GET /superadmin/orgs/{slug}/keys` | superadmin | the organisation's current org and demo keys (unsealed) |
| `POST /superadmin/orgs/{slug}/rotate` `{kind}` | superadmin | revokes that kind's key, issues and seals a new one |
| `POST /superadmin/orgs/{slug}/deactivate` | superadmin | `active = false`, keys refused, `deactivateOrg` on chain; org1 cannot be deactivated (it is the pipeline fallback) |

- **Superadmin is not an organisation.** Like `admin`, it holds no `org_id`, so every organisation route refuses it
  (`get_scope`); it reaches an organisation's data only by opening that organisation's console with its key.
  Org, demo and admin keys get 403 on `/superadmin/*`.
- **Login throttling.** 5 failed attempts per minute per client, 30 per minute in total, then 429 with
  `Retry-After`. The client is `CF-Connecting-IP` when present (the tunnel), else the socket address. The API listens
  on 127.0.0.1 only, so only the tunnel and this laptop can reach it.
- `auth.lookup` additionally refuses keys of inactive organisations and expired sessions.
- New organisation slugs are derived from the name (`shopsafe-soc`), unique; names unique.

## 5. Sector routing (pipeline)

- Triage already records `brand_matched`; every brand in `data/brands.yaml` has a `sector`.
- When the triage worker queues a new candidate for confirmation, it tags it with the **oldest active organisation in
  that brand's sector** (ties broken by id, so org1 before org2): queue item `"<org_id>:<domain_id>"` (the format the enrich worker already accepts). A sector
  with no organisation, or a candidate without a brand, is queued untagged and confirmed on behalf of
  `PIPELINE_ORG` (org1), exactly as today. The sector → organisation map is cached for 60 s.
- One fetch per domain, as today: fetch load does not change.
- If two organisations share a sector, only the oldest receives that sector's confirmations (stated limit; the
  other still sees the shared feed and its own seeded campaign).
- `GET /candidates` gains an optional `sector` filter (brands of that sector). The Live queue shows the signed-in
  organisation's category by default, with an "All sectors" toggle. Category `other` defaults to all sectors.
- **Measurement (§9):** `scripts/evaluate.py` response time currently measures only `PIPELINE_ORG`'s verdicts. It
  changes to every organisation's verdicts on live sources. Each live domain is confirmed by exactly one
  organisation, so nothing is counted twice, and with no non-banking organisation the result is identical to today.
  The report is regenerated by `npm run finalize`, never hand-edited.

## 6. Seeded campaign and demo reset

- On creation, `seed_campaign` builds a campaign for the organisation: ~60 domains imitating `demo_brand` (default: the
  first brand of its sector in `brands.yaml`; required when the category is `other`), labelled **seeded** exactly as
  today's, with a signed evidence bundle, and published to the chain as that organisation so `/ledger/by-kit` finds it.
- `POST /admin/reset` re-seeds **every** active organisation: org1 (470, ICICI), org2 (50, HDFC, same kit) unchanged,
  each other organisation its ~60-domain campaign. Live CT data and its verdicts are kept, as today.

## 7. Ledger: an account per organisation

- On creation the API generates an account (`eth_account`), seals its key, funds it from the chain admin (Hardhat #0)
  and calls `OrgRegistry.registerOrg(address, name)`. `CHAIN_ADMIN_PRIVATE_KEY` (Hardhat #0, public, demo chain only)
  joins `.env`; nothing changes on the contracts.
- `Ledger.from_settings` loads org1/org2 from `.env` as today plus every organisation with a sealed key from the
  database (refreshed when one is created).
- A fresh demo chain (`demo up` → deploy → reset) re-registers every active organisation from the database before
  re-anchoring. Deactivation calls `deactivateOrg`.
- If the chain is down at creation, the organisation is created anyway and registration is retried by the next
  `demo up` (the panel shows "chain: pending").

## 8. Console (`apps/console`, `docs/DESIGN.md` unchanged)

- **Login page** (replaces the key form in `KeyGate`), two tabs:
  - **Organisations**: `GET /orgs/public` grouped by category; each row shows name, the read-only key (copy) and
    **Sign in (read-only)**. Below: "Have a full key? Paste it" (the current field).
  - **Super admin**: email + password → session token, stored where the key is stored today.
- **Super admin panel** (`/superadmin`, rendered instead of the organisation console for a superadmin session):
  organisations table (name, category, active, chain status, created); **New organisation** form (name, category,
  demo brand); reveal + copy keys; rotate; deactivate; **Open console as this organisation** (switches the stored key
  to that organisation's org key); sign out (revokes the session).
- The left rail shows the organisation's category under its name. Generic copy says "organisation", not "bank".
- The API URL comes from the runtime lookup in §10, with `VITE_API_URL` as the fallback.

## 8b. Explaining the system: Technical approach, How it works, and a ? on every page

Three pieces, all open without a key, all following `docs/DESIGN.md`, all bound by the content rules below.

**Content rules (every explainer, every step, every help panel).**
- No measured number is typed into explainer text. A figure is either read live from the API at display time (the
  tour shows the current coverage from the sweep endpoint) or the text points to the Metrics page, where measured
  values already live. Same rule as `docs/REPORT.md`.
- A candidate is "suspicious, not verified"; only confirmed means two independent strong signals (CLAUDE.md §2.2).
- The takedown-selection framing is used verbatim: *"Takedown-set selection is formulated as a QUBO. It runs on
  OR-Tools CP-SAT in production; the same formulation runs on QAOA. Quantum is not in the critical path."* The word
  "quantum" never appears in a heading, a nav item or a step title (CLAUDE.md §2.3).
- Stated limits are stated: HTTP-only phishing has no certificate; wildcard certificates hide the subdomain; the
  live pipeline currently ends at the confirmation gate (0 live confirmations, with the measured cause).

**Technical approach (`/technical`, public, static).** One page, sections in this order: the problem (why blocking
URLs is too late; the base-rate argument: a classifier alone cannot work at this volume); the five stages (ingest
from Certificate Transparency, triage, confirmation by evidence, campaign clustering, interdiction) with the method
of each; evidence and chain of custody (artifacts hashed into a Merkle root, Ed25519 signature, root anchored);
the ledger (what goes on chain and what never does; the four reasons it exists); takedown selection (maximum
coverage, the verbatim framing above); the platform (organisations, categories, row-level security, sector routing);
how it is served (laptop, tunnel, Supabase, Vercel); stated limits. Reuses the Architecture diagram in a static
mode (no status squares without a key). Linked from the login page and the left rail.

**How it works (`/tour`, a guided tour of the real pages).**
- Started from the login page ("How it works") or the left rail. Started signed out, it first signs in read-only
  as Bank One with its published demo key (`GET /orgs/public`), then runs on live data.
- About 11 steps, each `{route, target, title, text}`: Architecture (the pipeline) → Live queue (certificates
  arriving) → a candidate's score (triage nominates, never red) → the Confirmed filter (two strong signals) →
  campaign graph (shared infrastructure) → budget slider and coverage (maximum coverage) → solver table (CP-SAT in
  production, the framing) → abuse report (generated, never sent) → evidence (Merkle root, signature, Verify) →
  Ledger (a kit hash finds another organisation's campaign, nothing else shared) → Metrics (everything measured).
- Each step navigates to its route, highlights the target element (marked in the page with `data-tour="…"`) and
  shows a card: "Step 5 of 11", title, text, **Back**, **Next step**, **Exit**. Keys: ← → Esc. Focus moves to the
  card; the step is announced to screen readers.
- Items the steps need (a campaign, a bundle, a kit hash) are looked up through the API at run time, never hard-coded
  IDs. If a target is missing (no data yet), the card still shows and says what would be there.
- The tour only highlights; it clicks nothing and changes nothing (it runs fine on a read-only key).

**? on every page.**
- A **?** button at the same place in every page header (and on the login page and the super admin panel) opens a
  side panel: *What this page is* · *How to read it* (each element on the page) · *Where the data comes from* ·
  *What it does not claim*. Esc or ✕ closes it.
- All help text lives in one file (`apps/console/src/help/content.ts`, keyed by route) so wording is reviewed in one
  place; a test fails if any route lacks an entry.

## 9. Changes to earlier decisions (owner-approved 2026-10-09)

1. **Keys are retrievable** (sealed) instead of shown once; read-only keys are **published** on the login page for
   every organisation (until now only Bank One's demo key was to be published, `DEPLOY.md` §6).
2. **Live candidates are routed by sector** instead of all being confirmed for Bank One.
3. **Response-time measurement** covers every organisation's live verdicts (§5).
4. **A password login exists** (super admin only); every other access is still by key.
5. **The public site is served from the owner's laptop** through a quick tunnel; Railway stays documented, not used.
6. **The Supabase publishable key is used by the console** (to read the current API URL), where `DEPLOY.md` said no
   deployed service uses it. It reads one public row and nothing else (§10).

## 10. Public site: quick tunnel + URL discovery

No Cloudflare account, no domain. A quick tunnel's URL changes on every start, and the console's `VITE_API_URL` is
fixed at build time, so the console looks the current URL up at runtime instead of being rebuilt.

**Publishing the URL (laptop).**
- New table `public_endpoints` (`name text primary key`, `url text not null`, `updated_at timestamptz`). Row-level
  security on; one policy: role `anon` may `select`. No role but the privileged owner connection may write. The
  policy is created only where the role `anon` exists (Supabase), so `schema.sql` still applies to the local test
  database.
- `scripts/tunnel.py` runs `npx cloudflared tunnel --url http://127.0.0.1:8000`, reads its output for the
  `https://<random>.trycloudflare.com` URL, checks `<url>/health` answers, then upserts row `api` with it, and keeps
  running. If cloudflared exits, the wrapper exits; the supervisor restarts it, which publishes the new URL.
- `scripts.demo up` starts it detached and supervised like the other processes; `check` gains a row: the published
  URL's `/health` answers through the tunnel.

**Finding the URL (console).**
- Build-time settings on Vercel, set once: `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY` (an
  `sb_publishable_` key, designed to be public), and `VITE_API_URL` as the fallback.
- On start the console fetches `<VITE_SUPABASE_URL>/rest/v1/public_endpoints?name=eq.api&select=url` (header
  `apikey`), 3 s timeout. It accepts the URL **only** if it matches `^https://[a-z0-9-]+\.trycloudflare\.com$`;
  anything else, or no answer, means `VITE_API_URL`. This keeps an altered row from sending visitors' keys elsewhere.
- If an API call fails at the network level, the console re-reads the row once and retries (the tunnel may have
  restarted mid-session).
- Without the two Supabase settings (local builds, the offline e2e) nothing changes: `VITE_API_URL` as today.

**API side.** `.env`: `CONSOLE_ORIGINS=https://q-cert-chain.vercel.app` (already set). The API stays on 127.0.0.1.

**Stated limits.** Cloudflare offers quick tunnels for testing, with no uptime guarantee. The site works only while
the laptop is awake with the stack running. After a restart, visitors already on the page switch to the new URL on
their next failed call; a reload always picks it up.

## 12. Out of scope

Per-person user accounts and roles; more than one super admin; self-service sign-up; e-mail of any kind (the super
admin e-mail is a login name only; no code sends mail, CLAUDE.md §2.1); new brands or an Entertainment category;
Railway deployment; a named Cloudflare tunnel or custom domain; changing the confirmation rules.

## 13. Risks

- **`test1234` on a public site.** Whoever guesses it can reveal every organisation's full key. Throttling slows
  guessing; it does not make a weak password strong. Change `SUPERADMIN_PASSWORD` before the link is shared widely.
- **One shared read-only key per organisation** shares its 60 requests/minute among every visitor using it.
- **The laptop is the server**: sleep, a network drop or a dead stack takes the public site down (the supervisor
  restarts dead processes, not a sleeping laptop).
- **Quick tunnels are a testing service** with no uptime guarantee; if Cloudflare limits or drops one, the site is down
  until the supervisor's restart publishes a new URL. A named tunnel on an owned domain removes this (not built).
